# Focus 再次提醒可靠性、额度计数与紧急弹窗设计

状态：用户已确认方向，等待书面设计复核后进入实施计划。

## 目标

本轮先完善实时模式的基本提醒能力，再实现额度越少、弹窗越大的紧急视觉反馈：

- 预设与自定义“稍后提醒”都走同一套混合调度链路，自定义时间仅允许 1～60 分钟。
- 到期时只在原受关注应用仍位于前台时显示 Focus 自有的 AI 提醒；不得在设置等非关注应用上错误弹出旧会话提醒，也不得在用户以后重新打开原应用时补弹过期提醒。
- 只有 ReminderActivity 真正恢复到前台并准备显示弹窗时才消耗一次提醒额度。仅通知栏出现、调度到期、启动 Activity 失败都不扣额度。
- 首页准确展示“本时间段已提醒 X/Y 次，剩余 Z 次”。
- 基本提示功能通过自动化和 RMX3350 实时模式真机验证后，再启用按额度递增的弹窗尺寸；最后一次额度显示为内容区域全屏。

兼容模式不作为本轮完成声明的依据，后续单独验证并记录。

## 已确认的行为语义

### 稍后提醒到期

到期时按以下顺序处理：

1. 守护已关闭、会话已结束、当前打开会话已改变、原应用已不在关注列表或额度已满：跳过并清理该会话的稍后提醒状态。
2. 屏幕未解锁或当前前台状态暂时无法确认：返回 `RETRY`，继续使用现有 15 秒间隔、最多 20 次的短重试。
3. 已明确切换到其他应用，包括设置、桌面或另一个非目标应用：返回 `SKIP`，清空 `snoozeUntil` 并取消其余调度路径。
4. 已确认原会话的受关注应用仍在前台：原子领取本次稍后提醒，构造 Focus AI 文案并请求启动 ReminderActivity。

`SKIP` 是终态。被跳过的旧提醒不能在用户稍后重新打开原应用时复活。

### 时间范围

- 预设保留 1、5、10 分钟。
- 自定义输入只接受整数 1～60；空值、非数字、0、负数和大于 60 的值保持不可确认，不进行静默截断。
- ViewModel 和调度入口再次校验 1～60，避免未来新增入口绕过界面校验。
- 历史 SharedPreferences 中大于 60 的旧值在读取时兼容收敛为 60；新写入值不得超过 60。
- Android 11 优先使用现有精确唤醒；Android 12 及以上无精确闹钟能力时允许系统产生合理延迟，但仍使用 Focus ReminderActivity，不使用系统闹钟界面或铃声。

## 现有问题与根因

### 前台应用缓存失真

`RealtimeForegroundProvider` 当前只保存包名，不保存观测时间。ColorOS 冻结 Focus 进程后，无障碍事件停止更新；AlarmManager 唤醒进程时，`AndroidFollowUpEnvironment` 仍优先返回旧包名，而不会查询 UsageEvents。这样会把五分钟前的目标应用误判为当前前台应用，并在设置页面上弹出旧提醒。

### 额度按会话而不是按弹窗计数

`app_usage_sessions.remindedAt` 每个会话只有一个字段。首次提醒写入一次，后续提醒只覆盖同一行时间；`COUNT(*)` 因此最多把同一会话计为一次。通知出现但 Activity 未显示时也可能提前更新该字段，无法表达“实际弹出一次才扣一次”。

## 方案比较

### 方案 A：新建实际显示事件表，并为前台快照增加新鲜度（采用）

新增一条提醒显示对应一行事件，ReminderActivity 在恢复到前台时原子确认额度并写入事件。前台判断对实时缓存增加时间戳，缓存过期时主动读取 UsageEvents；无法确认则重试。

优点：准确表达首次与多次稍后提醒；通知不扣额度；支持滚动窗口、首页展示、AI 上下文和紧急程度；能直接修复真机发现的旧前台缓存。缺点：需要 Room 5→6 迁移，并调整提醒启动数据流。

### 方案 B：在会话表增加累计次数（不采用）

改动较少，但无法准确查询滚动时间窗口，也无法保留每次提醒的发生时间；后续重置额度和 AI 上下文会继续出现边界错误。

### 方案 C：继续使用 `remindedAt` 并在内存中补计数（不采用）

无法跨进程冻结、回收和重启保持准确性，也不能可靠区分通知与真实弹窗。

## 架构设计

### 1. 新鲜前台快照

把仅返回包名的接口改为返回带来源和观测时间的前台结果：

- `Confirmed(packageName)`：当前前台应用可确认。
- `Unknown`：权限不足、系统查询异常或没有可用事件。

`RealtimeForegroundProvider` 同时保存包名与 `elapsedRealtime`。到期执行时：

1. 实时缓存仍在很短的新鲜窗口内时直接采用。
2. 缓存已过期时查询 UsageEvents，选择最新的 `MOVE_TO_FOREGROUND` / `ACTIVITY_RESUMED` 事件。
3. 查询失败或无事件时返回 `Unknown`，不得再把未知视为目标应用。

Gate 对 `Unknown` 返回 `RETRY`；对已确认的其他包名返回 `SKIP`。诊断日志记录来源、缓存年龄和决策原因，但不记录 AI 文案、API Key 或用户隐私内容。

### 2. 实际提醒显示事件

Room 版本从 5 升到 6，新增 `reminder_display_events`：

- `id: Long`，自增主键。
- `attemptId: String`，本次展示尝试的唯一标识并建立唯一索引。
- `sessionId: Long`，关联原使用会话。
- `displayedAt: Long`，Activity 实际恢复到前台的时间。
- `kind: String`，取值 `initial` 或 `follow_up`，用于诊断和测试，不改变额度规则。

DAO/Repository 提供：

- 统计指定时间点之后的显示事件。
- 返回指定窗口内的显示时间列表，供现有 ReminderPolicy 与 AI 上下文使用。
- 在事务中执行“检查额度 → 按 attemptId 幂等插入 → 返回插入后的窗口计数”。额度已满返回空结果。
- 重置当前窗口额度时删除对应时间范围内的显示事件。

迁移时把每条非空 `remindedAt` 的旧会话转换为一条 `initial` 历史事件，保留升级前已经使用的额度。`remindedAt` 暂时保留，用作兼容历史记录和首次提醒去重，不再作为提醒额度的数据源。

### 3. 从请求启动到实际扣额

首次提醒和稍后提醒在调用 Launcher 前创建唯一 `attemptId`，同时传递 `kind`、窗口分钟数和额度上限。Launcher 的职责仍是尝试启动 ReminderActivity，并在无法覆盖显示时发布通知；此时不写显示事件。

ReminderActivity 完成会话仍有效的检查后，在首次 `onResume` 时调用 Repository 的原子确认接口：

1. attemptId 已存在：读取既有结果，不重复扣额。
2. 当前滚动窗口额度已满：关闭 Activity，不显示弹窗。
3. 插入成功：取得包含当前这次提醒的准确计数，再挂载 ReminderOverlay。

Activity 重建、`onStart`/`onResume` 重复回调和相同 Intent 重送都由 attemptId 去重。系统只发布通知但没有恢复 ReminderActivity 时，不产生事件、不扣额度。

### 4. 首页与 AI 上下文

首页、ReminderPolicy、FollowUpReminderGate 和 AI 提醒上下文统一读取 `reminder_display_events`，不再从会话行数推断提醒次数。首页文案统一为：

`本时间段（30 分钟）已提醒 2/5 次，剩余 3 次`

剩余次数最小为 0。额度重置后首页立即刷新为 0/Y；清除显示事件不会删除使用会话、应用打开记录或用户操作历史。

### 5. 额度驱动的弹窗尺寸

这一部分只有在基本提醒功能通过后才启用。ReminderOverlay 使用 Activity 原子确认返回的实际计数计算紧急进度：

`progress = (count - 1) / (limit - 1)`，结果限制在 0～1；当 `limit <= 1` 时直接为 1。

- 第一次：卡片宽度约 82%，高度至少为可用内容区的 50%。
- 中间次数：宽度和高度随 progress 单调递增，每次实际扣额后都比上一次大。
- 最后一次，即 `count >= limit`：卡片填满 Activity 可用内容区，取消外层圆角，呈现全屏紧急状态。

不隐藏系统状态栏和导航栏，不阻断“稍后提醒”“返回 Focus”“返回桌面”等已有操作。内容区域支持纵向滚动，避免小屏设备、横屏或大字体模式下按钮不可见。通知样式不随额度变化。

## 错误处理与一致性

- Activity 启动异常：保留通知但不扣额度；记录受控诊断日志。
- 事件插入冲突：按 attemptId 视为同一次展示，读取既有计数，不重复插入。
- 数据库写入失败：不显示无法计入额度的弹窗，关闭 Activity 并保留诊断信息，避免 UI 与首页数字不一致。
- 调度三路径竞争：继续使用 `claimSnooze(sessionId)` 保证只有一条路径发起 follow-up attempt；Activity 再使用 attemptId 保证展示确认幂等。
- 已确认切换至非目标应用：清除 `snoozeUntil`，取消协程、WorkManager 和 AlarmManager 路径，不发布新弹窗。
- 真正 force-stop：遵守 Android 平台限制，不宣称能够绕过；用户重新打开 Focus 后只恢复仍合法的状态，不补弹已跳过提醒。

## 实施顺序

### 第一阶段：基本提示功能

1. 统一 1～60 分钟校验与旧值迁移读取。
2. 为实时前台缓存增加时间戳，并让未知状态进入重试。
3. 新增显示事件表、迁移与 Repository 原子确认接口。
4. 首次提醒和 follow-up 都改为“Activity 实际显示才扣额”。
5. 首页、额度 Gate、重置逻辑和 AI 上下文统一使用显示事件。
6. 自动化测试通过后构建完整 APK，核对安装包来源，再做 RMX3350 实时模式 USB 验证。

### 第二阶段：紧急视觉

1. 增加纯函数计算紧急进度和尺寸，先用单元测试锁定边界。
2. ReminderOverlay 接入递增尺寸、最后一次全屏与滚动保护。
3. 在 RMX3350 上分别验证额度上限 1、3、5 时的尺寸变化和操作可达性。

## 测试与验收

### 自动化测试

- 自定义输入：1、60 有效；0、61、负数、空值和非数字无效；旧持久化 120 读取为 60。
- 前台判定：新鲜实时快照优先；过期快照改查 UsageEvents；已确认其他应用为 SKIP；未知为 RETRY。
- 旧会话在非目标应用到期后被清理，重新打开目标应用不会补弹。
- 三条调度路径竞争时仅创建一个 attemptId。
- 通知路径不写显示事件；Activity 首次恢复写一次；Activity 重建仍只写一次。
- 同一会话首次提醒加两次 follow-up 应计为三次，而不是一次。
- 原子确认在额度边界不会超过上限；首页、Gate、AI 上下文读取相同计数。
- 5→6 迁移把每条历史非空 remindedAt 转换为一条事件，空值不转换，重复迁移不产生重复事件。
- 紧急进度在额度 1、3、5 下单调递增，最后一次为 1；非法计数安全收敛。

### RMX3350 实时模式

使用完整构建和安装，不以 Apply Changes 作为证据。安装后先核对本地 APK 与设备 APK 来源/哈希，再测试：

1. 1 分钟、5 分钟和至少一个非预设自定义时间，在合理延迟范围内重新显示 Focus AI 弹窗。
2. 等待期间让 Focus 进入 frozen，确认 AlarmManager 能唤醒业务链路。
3. 到期时仍在原目标应用：弹窗出现且额度恰好增加一次。
4. 到期前切到设置或其他非目标应用：不弹窗、不扣额度，重新打开原应用后也不补弹。
5. 仅出现通知时：首页额度不增加；用户未看到弹窗不能被计费。
6. 锁屏到期后解锁，在重试窗口内按当前前台状态决定显示或取消。
7. 同一会话连续稍后提醒两次，首页次数逐次增加并与弹窗紧急程度一致。
8. 额度最后一次时弹窗占满可用内容区，所有操作按钮仍可点击。
