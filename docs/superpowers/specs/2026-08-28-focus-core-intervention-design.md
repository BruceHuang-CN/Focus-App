# Focus 核心监控与任务干预统一设计

状态：待用户书面审核；审核通过前不进入实施计划和 Android 正式代码修改。

## 1. 设计目的

Focus 的核心闭环统一为：

```text
当前任务 → 打开受关注应用 → Focus 提醒
→ 回到任务 / 有目的使用 / 休息一下
→ 30 秒和 120 秒观察 → 形成可解释的结果
```

本设计优先解决两件事：

1. 无障碍事件驱动的应用使用检测必须有明确状态、健康度和恢复边界。
2. 每次提醒从触发、实际展示、用户选择、计时恢复到结果分类都必须可持久化、可幂等重放、可测试。

本轮是在现有 Kotlin、Compose、Room、Hilt、无障碍服务、ReminderActivity、AlarmManager、WorkManager 和 AI 缓存基础上演进，不重新创建项目或更换整体框架。

## 2. 已确认的产品约束

### 2.1 提醒操作

- 提醒页只显示三个操作：`回到任务`、`有目的使用`、`休息一下`。
- `Ignore` 不是第四个按钮，而是后台根据行为证据推导的统计结果。
- 三个按钮有 6 种完整排列。随机开关开启时，每个新提醒选择一种排列，并排除上一次已使用的完整排列。
- 同一个提醒事件重新显示、Activity 重建、屏幕旋转或 Compose 重组时，必须读取已持久化的排列，不得重新洗牌。
- 设置页提供“随机排列提醒选项”。新安装和从旧版本升级都默认为开启；只有用户主动关闭后才使用固定顺序：`回到任务 → 有目的使用 → 休息一下`。
- 实际排列必须跟随事件记录保存，统计时可按位置校正选择偏差。

### 2.2 应用、双开和 AI 的关系

- 双开实例在产品上按同一种应用处理，共享提醒策略、目的预设和 AI 文案包。
- 能可靠识别不同包名的实例时，仅允许用户在设置中校准本地别名和应用族；不能可靠区分的同包名跨用户/容器实例不得显示为“已精确识别”。
- 不建立“通信沟通”“视频内容”等必须人工维护的 AI 场景分类，也不为每个应用单独请求 AI。
- AI 文案包按“当前任务快照 + 用户语气 + Prompt 版本”生成和缓存。运行时由本地模板槽位替换应用名称、目的、已使用分钟数和本次打开次数。
- 目的预设属于本地配置，不调用 AI。每个应用族可覆盖一组 4～5 个目的；未配置时使用全局默认目的。

### 2.3 重置操作

- 设置页保留一个合并操作：`重置提醒窗口和 AI 文案`。
- 一次点击同时开始新的提醒额度窗口，并使当前任务的 AI 文案包失效后请求重新生成。
- 不拆成两个按钮，不要求用户为应用逐个重置。
- 额度重置必须立即、本地、可靠；AI 刷新失败不能回滚额度重置，继续使用旧缓存或本地兜底，并明确显示局部失败状态。

### 2.4 可靠性边界

- 用户可见的监控模式只保留无障碍事件驱动模式，删除 UsageStats 兼容模式及相关模式选择 UI。
- 内部健康状态保留 `ACTIVE`、`DEGRADED`、`PERMISSION_REQUIRED`、`STOPPED`。
- AI 网络失败、进程重启、Activity 重建或调度重复都不得破坏计时、跳转、事件记录和结果分类。
- 真正 force-stop、OEM 冻结和系统阻止后台启动属于 Android 平台边界；未经新 APK 安装和真机验证，不宣称已经可靠解决。

## 3. 方案选择

### 方案 A：在现有框架内加入单一领域状态机（采用）

保留现有无障碍入口、Room、提醒 Activity 和多路径到期调度，把分散在 Service、Coordinator、Activity 和 session 字段中的决策收敛到纯 Kotlin 状态机与持久化事件模型。

优点：可以复用已完成的基础设施；每一步可渐进迁移和测试；故障证据与用户行为不再混在 UI 生命周期中。代价：迁移期间需要短期适配旧会话和旧调度接口。

### 方案 B：重写全部监控和提醒管线（不采用）

虽然结构可以一次统一，但会同时重做无障碍、数据库、调度、提醒 UI 和 AI，回归风险过高，也会丢失现有已验证的可靠性修复。

### 方案 C：继续扩展 `AppUsageSession.userAction` 和 `snoozeUntil`（不采用）

改动看似较少，但单字段无法表达一次提醒的排列、展示证据、多个期限、恢复状态和 30/120 秒观察，也无法准确区分 Ignore、未知和系统中断。

## 4. 架构边界

### 4.1 `FocusAccessibilityService`：事件适配器

职责仅限于：

- 接收被允许的窗口/前台变化事件。
- 过滤 Focus 自身、输入法、系统界面和无法归属应用的噪声。
- 把带时间、包名、事件类型和服务连接代次的观测交给 Guardian。
- 汇报服务连接、断开、事件停滞和权限状态。

它不直接创建提醒、不写用户决定、不生成 AI 文案，也不在回调中做网络或长耗时数据库工作。

### 4.2 `GuardianEngine`：纯 Kotlin 状态机

输入为前台观测、任务快照、受关注应用族、全局暂停状态和时间事件；输出为明确的领域命令：开始候选会话、确认进入、结束会话、请求干预、恢复计时器或记录未知。

Reducer 必须无 Android 依赖。相同状态和相同输入产生相同输出，以便使用虚拟时钟进行单元测试。

### 4.3 `InterventionCoordinator`：持久化与编排

负责：

- 在事务中创建或领取一次干预事件。
- 生成并保存按钮排列。
- 通过现有提醒展示协调器请求启动 Activity。
- 接收 Activity 的已展示确认和三个显式选择。
- 启动、延长、恢复期限，并把到期命令交给统一执行器。
- 防止无障碍回调、AlarmManager、WorkManager 和进程内定时器重复执行同一状态转换。

### 4.4 `ReminderActivity` 与 Compose UI：状态渲染器

Activity 只通过 `interventionId` 加载已持久化状态。Compose 根据状态显示文案、排列、目的选择或到期确认，并把用户意图交回 ViewModel/Coordinator。

UI 不自行洗牌、不自行判断 Ignore、不用 `remember` 作为计时事实来源。Activity 只有在已恢复前台并完成展示确认后，事件才从“请求展示”变为“已展示”。

### 4.5 `InterventionDeadlineScheduler`：统一期限调度

现有进程内、AlarmManager、WorkManager 三条路径继续作为唤醒手段，但都只携带 `interventionId + deadlineRevision`。到期后必须由数据库事务领取执行权，过期 revision 或已经完成的事件直接跳过。

### 4.6 `OutcomeObserver`：证据收集与结果推导

它只消费无障碍前台观测、屏幕/锁定状态、展示生命周期和期限事件，保存原始证据，再用纯规则推导结果。不得用一次缺失事件猜测用户意图。

### 4.7 `TaskReturnNavigator`：任务级返回目标

从干预创建时保存的任务快照读取目标，按目标类型执行并返回结构化结果。跳转失败不会伪装为成功，结果进入诊断和 30/120 秒观察。

## 5. 领域与持久化模型

### 5.1 当前任务快照

`CurrentTaskSnapshot` 在创建干预时冻结：

- `taskId`
- `title`
- `returnTargetType`：`FOCUS_TASK`、`APP`、`DEEPLINK`、`HOME`
- `returnPackageName`
- `returnDeepLink`
- `capturedAt`
- `taskRevision`

后续用户编辑或切换任务不改变已经出现的提醒语义；新提醒使用新快照。

### 5.2 应用族

`AppFamily` 保存稳定的本地 `familyId`、展示名、已确认包名集合和识别可信度。AI 只接收展示名，不接收“主应用/双开”身份。跨用户同包名而普通应用无法观察的情况记录为 `UNRESOLVED_CONTAINER`，UI 明示限制。

### 5.3 干预主记录

新增 `interventions`，一行代表一次完整干预：

- 身份：`id`、`sessionId`、`appFamilyId`、`observedPackageName`
- 快照：任务标题、返回目标、应用展示名
- 触发：`triggeredAt`、`requestedAt`、`displayedAt`
- 展示：`displayAttemptId`、`displayState`、`actionOrder`
- 选择：`decision`、`decisionAt`、`purposePresetId`、`purposeLabelSnapshot`
- 计时：`timerKind`、`startedAtWall`、`startedAtElapsed`、`deadlineWall`、`deadlineElapsed`、`bootId`、`extensionCount`、`deadlineRevision`
- 结果：`derivedOutcome`、`resolvedAt`、`evidenceQuality`
- 效果：`effectiveness30`、`effectiveness120`
- 审计：`createdAt`、`updatedAt`、`schemaRevision`

`decision` 仅取 `RETURN`、`INTENTIONAL`、`REST` 或空值。显式选择和后台结果分开保存，避免把“按了休息”错误统计为 Ignore。

### 5.4 观测证据

新增只追加、不覆盖的 `intervention_observations`：

- `interventionId`
- `kind`：前台变化、展示确认、Activity 不可见、屏幕锁定、系统中断、30 秒检查、120 秒检查、期限到期、健康变化等
- `observedAt`
- `packageName`（仅本机包名，不上传）
- `guardianHealth`
- `sourceGeneration`
- `detailsCode`

统计结果由证据和主记录推导。详细诊断遵循保留上限，不记录 AI Key、完整文案、通知内容或页面文本。

### 5.5 目的预设

`purpose_presets` 是纯本地表：

- `id`
- `appFamilyId`，空值表示全局默认
- `label`
- `defaultDurationMinutes`
- `sortOrder`
- `enabled`

同一应用族的所有双开实例共享目的。应用族未配置时使用 4～5 个全局默认目的。提醒发生时只选择，不要求临时输入；标签快照写入干预，后续编辑不改历史。

### 5.6 设置与迁移

- 数据库由当前 v6 迁移到 v7。
- `settings` 新增 `randomizeReminderActions INTEGER NOT NULL DEFAULT 1`。迁移 SQL 明确把所有既有行设为 `1`，确保旧用户升级默认开启。
- 旧 `detectionMode=compatibility` 迁移为 `realtime`；设置 UI 删除模式选择。
- 历史 `AppUsageSession`、`reminder_display_events` 和 AI 缓存不删除。旧字段暂时只读兼容，新的领域逻辑不再写入 `userAction` 表达干预结果。
- 升级时未到期的旧 `snoozeUntil` 缺少新语义和可靠 revision，首次启动时取消其遗留调度、清空该期限并写一条迁移诊断；不把它猜成“有目的使用”或“休息”。

### 5.7 提醒额度窗口

新增单行 `reminder_quota_epoch`，保存 `epochId` 和用户最近一次主动重置的 `startedAt`。额度统计仍以现有滚动窗口为基础，但查询下界取：

```text
max(当前时间 - reminderWindowMinutes, epoch.startedAt)
```

合并重置只推进 epoch，不删除 `reminder_display_events` 或干预历史；这样首页立即归零，同时历史审计和长期统计仍然完整。旧版本升级时 epoch 从迁移时刻开始，但既有显示事件继续保留为历史，不计入新架构启用后的当前额度。

## 6. Guardian 状态机

### 6.1 监控健康度

- `ACTIVE`：无障碍已连接，权限有效，近期持续收到可解释事件。
- `DEGRADED`：服务仍连接，但事件时间出现异常空洞、系统限制或关键观测不足。继续接收事件，但需要未知优先。
- `PERMISSION_REQUIRED`：服务未授权、授权被撤回或配置不可用。
- `STOPPED`：用户关闭 Guardian；不自动引导为权限错误。

健康度与用户是否正在某个应用中是两个独立维度，不得用 `ACTIVE` 代替前台证据。

### 6.2 会话状态

- `IDLE`：没有受关注应用会话。
- `ENTER_PENDING`：刚观测到目标应用，等待短防抖与任务/暂停校验。
- `TARGET_ACTIVE`：目标应用会话有效，累计时长和打开次数。
- `INTERVENTION_ACTIVE`：该会话已有未完成干预，不重复创建。
- `SUPPRESSED_INTENTIONAL`：有目的使用计时中。
- `SUPPRESSED_REST`：全局休息暂停中。
- `EXIT_PENDING`：刚离开目标应用，等待短防抖避免系统浮层造成假离开。

### 6.3 关键规则

- 只有健康度可用、有当前任务、Guardian 开启、应用属于受关注族且不在有效暂停中，才能创建新干预。
- `SUPPRESSED_INTENTIONAL` 只抑制当前应用族的重复提醒；`SUPPRESSED_REST` 抑制所有应用族。
- 系统权限框、输入法、通知栏和 Focus ReminderActivity 不得结束原会话或触发新会话。
- 服务重连后先恢复数据库状态，再接受新事件；无法补齐的时间段标为未知，不使用 UsageStats 反推。
- 应用“打开次数”按经过防抖的 `IDLE/其他应用 → TARGET_ACTIVE` 转换计数，不按原始无障碍事件条数计数。

## 7. 干预生命周期与幂等

```text
DETECTED → DISPLAY_REQUESTED → DISPLAYED → DECIDED/TIMED
                    ↘ DISPLAY_FAILED
DISPLAYED/DECIDED/TIMED → OBSERVING → RESOLVED
```

### 7.1 创建与排列

1. Coordinator 原子检查当前会话是否已有活跃干预。
2. 读取设置和最近一次已展示干预的排列。
3. 随机开启：从 6 种排列中过滤上一排列，再从剩余 5 种选择；没有历史时从 6 种选择。
4. 随机关闭：保存固定排列。
5. 在同一事务中保存任务快照、应用族、排列和 `displayAttemptId`。

“最近一次”按实际 `displayedAt` 判断，不让展示失败的排列影响下一次可见提醒。

### 7.2 实际展示

- Launcher 发起 Activity 或发布通知不等于展示成功。
- ReminderActivity 首次进入可交互前台时，用 `displayAttemptId` 幂等确认 `DISPLAYED`，同时写入实际显示事件并消耗一次提醒额度。
- 仅创建展示请求、Activity 启动失败或只发布通知都不消耗额度。
- 在平台允许的确认窗口内未收到展示确认，记录 `DISPLAY_FAILED`；后续迟到的旧 Intent 不得复活已结束事件。
- Activity 重建只恢复原 `interventionId`，不增加提醒额度、不生成新排列、不重复记录展示。

### 7.3 重复调度

每次新期限或延长都递增 `deadlineRevision`。任一调度路径醒来后在事务中执行：

```text
事件仍活跃 && revision 相同 && deadline 已到 && 尚未领取
```

只有领取成功的路径可以继续执行。其余路径清理自身工作并退出。

## 8. 三个操作的行为

### 8.1 回到任务

1. 原子写入 `decision=RETURN` 和时间。
2. 立即关闭提醒 UI。
3. `TaskReturnNavigator` 按以下顺序尝试：任务级目标 → Focus 当前任务页 → 用户设置的通用返回目标 → 桌面。
4. 返回 Focus 当前任务页时，`MainActivity` 和导航层必须实际消费快照中的 `taskId` 并打开该任务上下文，不能只把 ID 放进 Intent 后停留在普通首页。
5. Deep Link 必须显式校验 scheme、可解析 Activity 和允许的包；失败继续下一层并记录原因。
6. 在 30 秒和 120 秒检查任务路径是否保持有效。点击只代表决定，不等于跳转或结果成功。

### 8.2 有目的使用

1. 用户从当前应用族的 4～5 个本地预设目的中选择，并确认时长。
2. 保存目的标签快照、`decision=INTENTIONAL`、开始时间和双时钟期限，立即关闭 UI。
3. 到期时：
   - 已回到任务路径或离开所有受关注应用：静默结束并记录有效返回证据。
   - 仍在该应用族：重新显示同一干预的到期阶段。
   - 位于另一个受关注应用：结束原应用的有目的使用，并按 Guardian 规则为新应用决定是否创建新干预。
   - 锁屏或证据不足：不强行弹窗，保留通知/延后检查并标记证据不足。
4. 到期页可快速延长 5 分钟。前两次直接延长；连续使用两次延长后，再次继续必须重新选择目的，确认后开启新计时段。
5. 每次延长增加 revision 并重新持久化期限，不能只依赖内存协程。

### 8.3 休息一下

1. 保存 `decision=REST`、休息期限并立即关闭提醒。
2. 休息是全局暂停，期间所有受关注应用均不创建新提醒，但前台观测继续用于到期判断。
3. 到期时：
   - 已处于任务路径或非受关注应用：静默恢复 Guardian，并记录实际已返回。
   - 仍处于任一受关注应用：恢复提醒流程。
   - 锁屏、电话或系统界面：不强行弹窗，等待下一条可信前台事件或发布可控通知。
4. 进程或设备重启后根据持久化期限恢复；已经过期则立即执行同一到期判断，不重新赠送完整休息时长。

## 9. 时间与重启恢复

运行中同时保存 wall clock 和 `elapsedRealtime` 期限：

- 同一次开机且 `bootId` 一致时，以单调时钟为准，避免用户修改系统时间影响计时。
- 重启后单调时钟不可比较，使用 wall deadline 恢复；检测到明显时钟回拨或异常跨度时，不把缺失行为分类为 Ignore，而是进入 `UNKNOWN`/待用户确认。
- 调度器只负责唤醒，数据库期限才是事实来源。
- Focus 冷启动、无障碍重连和 `BOOT_COMPLETED` 入口都调用同一个恢复器；恢复器按事件 ID 和 revision 幂等。

## 10. 30 秒与 120 秒效果观察

两个检查点都保存独立状态：`EFFECTIVE`、`INEFFECTIVE`、`UNKNOWN`。

- `RETURN` 从用户选择或成功发起返回跳转的时刻开始观察。
- `INTENTIONAL` 和 `REST` 从约定期限到达或用户提前结束计时的时刻开始观察，不能因为用户在获准时段内仍使用应用而判为无效。
- 没有显式选择的提醒，从其可交互生命周期结束时开始观察。

- 任务路径：任务 Deep Link 的目标包、Focus 当前任务页，或用户明确配置的任务应用。
- 受关注路径：任一受关注应用族。
- 其他应用/桌面不能自动证明完成任务，可记录为“已离开分心应用”，但效果状态保持保守。
- 观察期间健康度下降、锁屏或关键事件缺失时为 `UNKNOWN`，不补猜。

统计可分别回答“30 秒内是否离开分心应用”和“120 秒后是否仍保持”，不把一次点击直接当作有效。

## 11. Ignore 与结果分类

`derivedOutcome` 只用于没有正常完成证据或需要解释未选择的情况：

- `NO_RESPONSE`：提醒已确认展示且处于可操作状态，等待窗口内没有选择；没有锁屏/系统中断，并有可信证据表明用户仍在目标应用。
- `BYPASSED`：提醒已展示，随后被覆盖、绕开或消失，且用户继续或重新进入目标应用；必须有明确生命周期和前台证据。
- `IMPLICIT_RETURN`：没有点击任何操作，但可信观测显示用户进入任务路径。
- `DISPLAY_FAILED`：展示请求未在确认窗口内变为可交互展示。
- `UNKNOWN`：无障碍断开、进程/OEM 冻结、观测缺失、时间异常或证据冲突。
- `INTERRUPTED`：锁屏、电话、系统权限页等外部事件打断了可操作窗口。

只有 `NO_RESPONSE + BYPASSED` 在统计层汇总为 Ignore。优先级为：

```text
DISPLAY_FAILED / INTERRUPTED / UNKNOWN（证据门槛）
→ IMPLICIT_RETURN（明确任务路径）
→ NO_RESPONSE 或 BYPASSED（明确继续使用）
```

证据不足永远不降级成 Ignore。分类器版本随事件保存，未来修改规则时可以区分旧统计口径。

展示满 30 秒仍未选择时只追加一条“尚未响应”观测，不自动关闭弹窗，也不立即把最终结果锁死。之后若用户完成显式选择，最终统计以该选择和后续效果为准；只有本次提醒的可交互生命周期最终结束、始终没有选择且继续使用证据满足门槛时，才落为 `NO_RESPONSE`。若提醒失去前台后目标应用恢复并持续，则落为 `BYPASSED`；失去前台后的去向不明则为 `UNKNOWN`。

## 12. AI 多阶段文案包

### 12.1 缓存键与生成次数

缓存键为：

```text
taskSnapshotHash + toneKey + promptVersion + locale
```

不包含应用包名、双开实例、分钟数或打开次数，因此同一当前任务下所有应用共享一份文案包。切换任务、改变语气、Prompt 升级或用户点击合并重置时才失效。

### 12.2 文案包结构

一次网络请求返回受控 JSON，至少包含：

- 初次打断：2～3 条短句
- 有目的使用到期：2～3 条短句
- 延长后再次到期：2～3 条短句
- 休息结束：2～3 条短句
- 30/120 秒未改善时的温和召回：2～3 条短句

文本允许的本地槽位仅为 `{task}`、`{app}`、`{purpose}`、`{minutes}`、`{openCount}`。每次展示在对应阶段的本地候选中随机选择并替换，不产生新的网络请求。

### 12.3 失败策略

- 严格校验 JSON、阶段完整性、长度和槽位白名单。
- 新包生成失败时优先继续使用同任务的旧包；没有旧包时使用随 APK 提供的本地模板。
- 网络请求不阻塞提醒展示、计时、跳转或状态机。
- API Key 继续使用现有加密存储，不写事件或诊断。

### 12.4 合并重置

点击 `重置提醒窗口和 AI 文案` 后：

1. 事务性写入新的额度窗口 epoch，使首页和 Gate 立即按零开始。
2. 清除当前任务文案包的本地轮换游标，标记缓存需要刷新，后台发起一次文案包请求。
3. UI 显示“提醒次数已重置；文案刷新中/成功/仍使用旧文案”。
4. 重复点击期间只允许一个当前任务刷新请求在途，避免 Token 浪费。

## 13. 设置和诊断界面

“设置 → 提醒行为”包含：

- 随机排列提醒选项（默认开）。
- 目的预设入口。
- 休息和有目的使用默认时长。
- 合并的“重置提醒窗口和 AI 文案”。

“监控与诊断”只显示一种监控方式及当前健康状态，不再出现“实时/兼容”切换。诊断解释需要区分：未授权、用户停止、事件降级、系统限制和无法识别双开；不得把这些情况统称为“正在正常监控”。

## 14. 并发、异常与隐私

- 所有领域状态转换通过 Repository 事务执行，使用事件 ID、attempt ID 和 revision 去重。
- 协程作用域由 Service、ViewModel 或应用级组件显式持有；不使用无所有者的全局协程。
- 数据库写入失败时不展示一个无法追踪的干预；记录本地受控诊断并允许下次事件重试。
- 关闭 Guardian 后取消新的提醒和有效调度，但保留历史统计；重新开启不补弹停用期间的旧提醒。
- 不读取页面正文、聊天内容、输入文本或通知内容；仅保存完成本功能所需的包名、时间、选择和健康证据。
- 诊断导出只能由用户主动触发，导出前可预览；不静默上传。

## 15. 验收标准

### 15.1 领域单元测试

- Guardian 的进入、离开、防抖、系统浮层、停止、权限丢失和重连。
- 随机开启时 6 种排列可达、连续不重复；随机关闭时固定；同一事件恢复不变。
- 三条调度路径和 Activity 重建只完成一次状态转换。
- 有目的使用到期、两次延长、第三次重新选目的及进程重启恢复。
- 全局休息期间跨应用抑制、到期静默返回或重新提醒。
- 结果分类覆盖 6 种结果；所有证据不足路径均为 `UNKNOWN`，只有两种 Ignore。
- AI 缓存键不随应用、双开、分钟数和打开次数改变；合并重置只触发一次刷新。
- v6→v7 迁移确保所有新旧用户随机开关均为开启，并清理无法安全解释的旧 snooze。

### 15.2 Compose UI 测试

- 三种排列、目的选择、倒计时到期、延长和重新确认。
- Activity 重建后按钮顺序、目的、计时和当前阶段保持一致。
- 设置开关、合并重置进度和局部失败反馈。
- 大字体、小屏、横屏下三个核心操作可达，系统栏不遮挡。

### 15.3 集成和进程恢复测试

- 从无障碍事件到干预记录、显示确认、选择、期限和结果的完整链路。
- 冷启动、进程被回收、重启、Alarm/Work/进程内路径竞争。
- 删除 UsageStats 权限后核心路径仍可运行，应用内不再提供兼容模式。

### 15.4 真机边界

自动化通过后才构建新 APK，核对本地与已安装 APK 来源，再在 realme/ColorOS 和至少一台较新 Android 设备验证：

- 无障碍前台检测和系统浮层过滤。
- 后台限制、锁屏、电话、进程冻结和重启恢复。
- 三个动作、跳转回退、计时到期和 30/120 秒观察。
- 双开/应用分身能否被当前 OEM 可靠区分。

源码测试通过、浏览器原型通过或 APK 构建成功都不等于真机后台可靠。
