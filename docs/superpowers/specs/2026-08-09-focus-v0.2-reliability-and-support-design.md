# Focus v0.2：提醒可靠性、应用组与反馈支持设计

日期：2026-08-09  
状态：已确认，等待实现计划

## 目标

在不增加持续轮询、不引入自建后台服务的前提下，修复真实使用中的提醒可靠性问题，并加入首页提醒开关、可自定义且单选的应用组，以及轻量的反馈与支持入口。

本版本的优先级是：提醒不误弹、不误扣额度、跳转失败可解释；然后才是新的入口与配置体验。

## 已确认的产品决定

- 首页提供一个持久化的“守护中 / 已暂停”开关。
- “已暂停”只停止提醒，不停止无障碍或 UsageStats 检测；目标 App 的使用会话和统计仍继续记录。
- 恢复“守护中”只作用于之后新开始的目标 App 会话，不为已打开的旧会话补发提醒。
- 同一时间只能启用一个应用组。
- 应用组可创建、编辑、删除；组内应用由用户从已安装应用中选择。
- “当前自定义清单”是一个保留组：旧版已选择的目标 App 会迁移进入该组，手动编辑当前目标 App 时也更新该组，避免丢失已有选择。
- 反馈与支持页不做应用内文字反馈表单，也不自建服务器。
- 反馈与支持页保留问卷星二维码和链接、GitHub Issue 入口、微信公众号二维码/名称、赞助二维码/链接的展示位置。
- 未配置真实链接、名称或二维码时，对应入口显示“暂未开放”，不执行外部跳转。

## 当前问题与根因范围

### 1. 返回指定 App 失败

当前实现会读取已保存的包名，并通过 `PackageManager.getLaunchIntentForPackage()` 启动目标应用。链路中缺少三项保护：选择时的可启动校验、启动失败的异常分类，以及失败后的可见反馈。若包名无效、应用已卸载、没有启动入口或系统拒绝启动，用户会看到静默回退而不知道原因。

本次不假定具体设备上的唯一根因；实现会记录并展示实际失败类别，以便真机验证确认。

### 2. 离开目标 App 后仍显示提醒并占用额度

当前会话关闭时会尝试取消延迟任务，但已投递的通知或已启动的提醒页面缺少统一撤销。提醒写入 `remindedAt` 时也没有把“会话尚未结束”作为数据库更新条件；此外，兼容模式的前台状态最多存在一个轮询周期的延迟。这些因素会让旧会话在离开目标 App 后仍有机会展示提醒或占用窗口额度。

### 3. 无障碍看似被关闭

现有代码没有调用 `AccessibilityService.disableSelf()`，不能也不应私自重新开启系统无障碍。问题需要区分：系统服务是否启用、应用内实时检测开关是否启用、服务是否曾连接、何时中断。当前缺少这些可见状态和历史记录。

## 设计

### A. 提醒可靠性与指定 App 跳转

#### 会话关闭即撤销提醒

`SessionReminderScheduler.cancel(sessionId)` 扩展为同时完成三件事：取消延迟 Job、取消该会话对应的通知、通知正在显示同一会话的提醒页面自行关闭。通知 ID 继续由会话 ID 稳定计算，确保只取消自己的提醒。

提醒页面在首次显示前检查“当前打开会话 ID 是否仍等于自身 sessionId”；不相等时直接关闭，不渲染文案和按钮。收到同会话的撤销事件后也立即关闭。

会话关闭、应用组切换移除当前目标 App、首页暂停提醒都走同一条撤销路径。

#### 防止旧会话扣额度

数据库的“首次标记已提醒”更新增加 `endedAt IS NULL` 条件；跟进提醒的更新同样要求会话未结束。调度器保留触发前的前台校验，并在展示前再次确认当前会话 ID。这样已结束会话无法成为新提醒的额度记录。

会话关闭和提醒展示之间仍可能出现极短竞态，因此页面级校验和撤销通知是必须的第二、第三道防线。

#### 指定 App 跳转结果可见

引入明确的启动结果：成功、未选择应用、应用不可启动/已卸载、系统拒绝启动。选择指定 App 时验证它仍有启动入口；点击“去指定应用”时再次解析并捕获启动异常。

成功才关闭提醒页面。失败时保留当前提醒页面，显示简短原因和明确的“返回桌面”兜底操作，不再静默跳回桌面。诊断信息只包含失败类别和包名，不包含用户任务、AI 文案或 API Key。

### B. 首页提醒开关与检测状态

新增轻量 `ReminderControlStore`，用现有 SharedPreferences 保存一个布尔值，默认“守护中”。它不进入统计数据库，不需要数据库迁移。

首页顶部显示当前状态和说明：

- 守护中：记录会话并允许按当前规则提醒。
- 已暂停：继续记录会话和统计，但所有新旧提醒都不展示。

暂停操作按顺序写入状态、取消所有待执行会话提醒、撤销当前提醒展示。调度器在延迟前、额度写入前和展示前均检查该状态。恢复后不追溯已经开始的会话，防止用户刚打开目标 App 时突然收到旧提醒。

无障碍状态页新增：系统服务状态、应用内实时检测开关、最近连接时间、最近中断时间和当前检测模式。`FocusAccessibilityService` 只记录连接/中断，不尝试自行开启系统服务。

### C. 单选自定义应用组

应用组采用一个小型 `AppGroupStore`，以 SharedPreferences + 现有 Gson 保存少量组配置，避免为少量本地配置增加多表关联或复杂查询。每组包含稳定 ID、名称、应用列表和是否为系统保留组。

首次升级时，现有 `settings.targetApps` 复制为不可删除的“当前自定义清单”。可提供一个包含抖音、哔哩哔哩、小红书常用包名的“短视频组”示例；激活时只保留当前设备实际可启动的应用，并对缺失应用显示提示。

应用组管理页提供：

- 当前启用组单选列表；
- 新建、重命名、编辑组内 App、删除自定义组；
- “当前自定义清单”不可删除，但可编辑；
- 切换应用组时一次性替换 `settings.targetApps`；
- 手动在原目标 App 页面编辑时，同步更新当前启用组。

切换或编辑导致当前前台 App 不再属于目标 App 时，关闭该会话并撤销其提醒，但已有使用记录仍保留在统计中。

### D. 反馈与支持页

新增“反馈与支持”路由，展示四个独立卡片：

1. 问卷星反馈：二维码、链接按钮；
2. GitHub：仓库与 Issue 页面入口；
3. 微信公众号：二维码、名称和复制名称按钮；
4. 赞助支持：一个或多个二维码/外部链接。

外部链接使用系统浏览器或对应 App 的 `ACTION_VIEW`，启动失败时显示提示。所有可变信息集中在 `SupportLinks` 配置及资源中；本次只创建安全的空配置和图像占位槽，不写入个人收款码、公众号或问卷地址。

## 非目标

- 不自建反馈上传服务、账号体系、支付功能或云端数据库。
- 不强制结束第三方 App，不尝试绕过 Android 权限模型。
- 不允许同时合并多个应用组。
- 不因暂停提醒而停止使用统计。
- 不承诺应用可自动重新开启被系统关闭的无障碍服务。

## 测试与验收

### 自动化测试

- 会话关闭后，初始提醒和跟进提醒均不会写入额度或展示。
- 已显示通知在关闭对应会话后被取消；提醒页面在会话失效时不渲染或自行关闭。
- 暂停提醒后：新会话仍写入统计，调度器不展示提醒；恢复后仅新会话可触发。
- 指定 App：未选择、无启动入口、启动异常、成功启动四种结果均可测试。
- 应用组：迁移当前目标 App、单选切换、编辑、删除、缺失应用过滤、切换时关闭旧会话。
- 反馈与支持页：空配置禁用入口；有效 URL 发出正确外部 Intent。

### 真机验收

在 Android Studio 安装的 Debug 包上，分别使用实时无障碍模式和兼容模式测试：

1. 打开目标 App，再返回桌面，等待超过提醒延迟和兼容模式一个轮询周期，不应出现提醒或增加额度。
2. 打开目标 App 后立即暂停守护，统计应增加、提醒不应出现；恢复后重新打开目标 App 才可提醒。
3. 选择一个已安装的指定返回 App，点击提醒按钮后应跳转；卸载或选择不可启动应用时应显示失败原因而非静默回桌面。
4. 切换应用组后，只对新组内应用检测；旧组的历史统计仍可查看。
5. 核对无障碍状态页的系统状态与 Android 设置页面一致。

## 实现顺序

1. 提醒撤销、会话有效性和指定 App 跳转诊断；
2. 首页“守护中 / 已暂停”开关与无障碍状态记录；
3. 单选自定义应用组；
4. 反馈与支持页；
5. 全量回归、真机验证、更新开发日志与 GitHub 分支。
