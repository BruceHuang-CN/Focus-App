## 1. 推荐方案与边界

采用原生 Jetpack Compose + Material 3 + 现有 Room 数据库，沿用首页的浅绿背景、白色圆角卡片和绿色强调色。图表使用现有 Canvas 能力，点击明细使用 Compose 控件；当前规模无需引入大型图表库、WebView 或服务端。

分阶段实现：

1. 明确并验证任务时段规则，解决过时段仍提醒的问题。
2. 建立真正的任务组与任务归属，完成参考图的任务页。
3. 先完成统计页外观与有可靠数据的指标。
4. 补齐历史记录和动作统计，再实现周／月／年提醒活动。
5. 统计页保留“今日状态”入口，后续另做内容。

任务页应做真实分组。只把现有任务画进几个固定标题下可快速预览，但不能支持新建组、移动任务、组级时段和当前任务组，因此不作为最终交付方案。

以下涉及行为的规则为推荐稿，尚不表示用户已批准新的调度语义。

## 2. 任务页

### 2.1 页面结构

- 顶部：任务标题、新建任务组按钮。保留现有底部四个导航入口。
- 任务组卡片：名称、预设图标、重复星期与时段、未完成任务数量、当前组标记、展开／收起按钮。
- 当前组默认展开，其他组默认收起；用户主动改变后的展开状态由页面保存。
- 组操作：设置时段、设为当前；更多菜单提供重命名、换图标、删除组。
- 组内任务：完成勾选、标题、有效时段或“跟随任务组”、更多菜单。
- 任务操作：设为当前任务、编辑、移动到其他组、删除。
- 卡片底部：添加任务。
- 大字体和小屏下组操作换行，不把任务标题和三个按钮硬塞一排。
- 已完成任务仍可查看、恢复，默认收在组内的已完成区域。

### 2.2 最小数据模型

现有 `FocusTask` 只有任务标题、完成状态、手动当前标记、时段及重复星期，没有任务组。

建议新增：

- `TaskGroupEntity`：id、名称、预设图标标识、排序、组级计划字段、创建／更新时间。
- `FocusTaskEntity.groupId`：任务归属；加索引并制定删除约束。
- `FocusTaskEntity.sortOrder`：稳定显示顺序，同时用于组内默认任务选择。
- 单独表示有期限的手动激活记录：groupId、taskId、startedAt、expiresAt、激活来源。不要继续用永久 Boolean 表示临时激活。

新增 `TaskGroupRepository`，扩展现有任务解析器；继续让提醒关联一个明确的任务 ID，不在一个组的所有任务之间随机选取 AI 文案。

首版用系统图标中的有限预设，不做自定义图片上传、嵌套组和拖拽排序。

### 2.3 时段与“当前”规则（建议）

推荐首版：新任务默认跟随组时段，组内只突出一个当前任务，完成后按显示顺序选择下一项未完成任务。

需要定义：

| 场景 | 推荐行为 |
|---|---|
| 设置组时段 | 明确选择每天／工作日／自定义星期；不能显示了时间却没有任何生效日期 |
| 到达开始时间 | 激活这个组，选择上次指定且未完成的任务，否则选择第一项未完成任务 |
| 到达结束时间 | 结束这段计划的提醒资格，取消属于该计划的未展示提醒、稍后提醒和倒计时通知 |
| 时段内点“设为当前” | 选择该组／任务，有效期仍截止于计划结束 |
| 时段外点“设为当前” | 打开“临时专注”设置，明确持续时间；不静默永久覆盖时段 |
| 无时段的组 | 手动开始时选择期限，并可随时结束 |
| 组内所有任务完成 | 清除当前任务并显示已完成，不随意回退到过期任务 |
| 两个组时段重叠 | 首版阻止保存并提示冲突，避免建立复杂优先级 |
| 无有效任务 | 按本次反馈建议暂停任务提醒；是否保留独立的通用防沉迷提醒属于待确认产品决定 |

新任务默认只有组级时段。旧任务迁移时保留原有时段作为显式覆盖，不能为了界面整齐直接覆盖历史计划。若以后开放组内单独时段，任务有效窗口取组窗口与任务窗口的交集，并清楚显示例外。

首版继续限制单段结束时间晚于开始时间，不暗中新增跨午夜计划。未来需要 23:00–01:00 时另补跨日规则及测试。

### 2.4 数据迁移

当前数据库版本是 6，实施前重新核对，使用当时的下一个版本。

- 保留原任务 ID、完成状态、历史会话关联及时间设置。
- 有有效计划的旧任务按相同开始／结束时间与重复星期归入组；无计划任务归入“未分组”。
- 异常旧配置，如有时间但重复掩码为 0，保留并显示“需确认生效日期”，不擅自改成每天。
- 旧的永久手动激活若已超出计划，不迁移为永久豁免；提示重新选择临时期限定。
- 删除组时明确选择移动任务到“未分组”或删除组内任务。历史统计不能级联删除。
- 使用 Room 迁移测试验证升级前后 ID、归属、时段、历史引用；不能通过清空数据库解决升级。

## 3. “过了时间段仍提醒”的代码调查

### 3.1 已确认的代码行为

| 源码位置（相对项目根目录） | 观察结果 | 影响 |
|---|---|---|
| `domain/task/ActiveTaskResolver.kt`，位于 `app/src/main/java/com/example/focus_app/` 下 | 先找时段内任务，找不到后回退到任意未完成且 `isManualActive` 的任务；回退不检查该任务原时段 | 设过“当前”的任务到期后可能继续被选中 |
| `data/local/dao/FocusTaskDao.kt` | `setManualActive` 只切换 Boolean，没有截止时间 | 手动当前状态可持续跨越计划结束及重启 |
| `ui/tasks/TaskEditorScreen.kt`、`data/repository/TaskRepository.kt` | 默认重复掩码为 0；验证允许这种配置保存，而解析器要求星期匹配 | 单独设置开始结束时间不一定建立有效自动计划 |
| `service/AppSessionCoordinator.kt` | 进入目标应用时取一次当前任务 ID，并允许 taskId 为 null 创建会话和调用提醒调度 | 没有有效任务也可能触发通用提醒 |
| `service/ReminderScheduler.kt` | 延迟结束检查前台、会话和额度，展示前未复核任务有效时段 | 在结束时间之前排出的提醒可跨越边界 |
| `service/FollowUpReminderGate.kt`、`FollowUpReminderExecutor.kt` | 输入与执行路径未包含任务有效期，使用会话保留的 taskId 获取文案 | 稍后提醒可以继续引用已过期任务 |

`TaskRepository` 已有按下一时段边界更新当前任务的机制；不能简单认定为“完全没有计时器”。问题在于手动回退、无任务仍提醒及提醒执行资格没有统一约束。

例子：任务 16:50–17:30，曾点“设为当前”。17:30 后时段匹配失效，但它仍可能被手动回退选中；另一个例子是 17:29 选择 5 分钟后提醒，现有稍后提醒入口并不检查 17:30 截止。

以上是源码路径证据，尚未复现用户手机上的那一次现象，不能宣布已锁定唯一现场根因或已经修复。

### 3.2 排查与修复计划

1. 用可注入 Clock 写最小回归：手动任务＋计划到期、无重复星期、无有效任务、初次延迟跨边界、稍后提醒跨边界。
2. 分离“用于统计的应用使用会话”与“当前可展示的任务提醒资格”，避免为取消提醒直接截断仍在发生的使用统计。
3. 统一得到 taskId、activationId、validUntil 和激活来源；排程携带这次激活身份，过期或切换后旧回调不能冒用新计划。
4. 根据明确的产品规则，在时段边界主动取消任务提醒；首次提醒、稍后提醒、进程恢复及最终展示前均复核资格。
5. 首页当前任务订阅有效任务变化。目前首页刷新时只取一次值，需验证页面停留在前台跨边界时是否同步更新。
6. 避免高频轮询，复用现有时间边界、系统调度与恢复机制。
7. 设备验证时保留用户数据；测试 17:30 精确边界、锁屏后恢复、任务完成／删除／改时段、重启后的过期调度、相邻计划切换。

对已经显示的决策页，建议到期后撤销过期任务提示与强制重显资格；具体关闭或转换行为需在实施时统一，不能留下失去期限却持续拦截的页面。

## 4. 统计页

### 4.1 布局与范围

布局沿用参考图的四块：数据概览、提醒活动、使用情况、今日状态入口。

顶层保留“今天／最近 7 天／最近 30 天”，控制概览和行为分布；标题随范围变为“今日数据／最近 7 天数据／最近 30 天数据”。

提醒活动独立使用“本周／本月／本年”，标题旁显示实际日期范围，并支持前后翻期及返回当前期。这比“每日／每周／累计”更容易理解：前者是观察范围，后者混合了粒度和累计方式。

| 提醒活动范围 | 首选表现 | 补充 |
|---|---|---|
| 本周 | 周一至周日 7 根柱，每柱显示当天真实展示次数 | 图小且容易比较 |
| 本月 | 按星期对齐的月历热力图，一格一天 | 点击某日看次数与动作明细 |
| 本年 | 默认 12 个月汇总柱状图 | 若希望更贴近参考图，提供横向滚动年度日历热力图；不把一年强行压成无法点击的小点 |

年度热力图难度中等，主要是闰年、星期对齐、跨年边界、标签、点击与无障碍说明。提醒次数越多只表示干预越频繁，不代表更自律；避免把深绿色写成成绩奖励。

### 4.2 指标口径

| 图中指标 | 当前代码／数据情况 | 推荐处理 |
|---|---|---|
| 打开次数 | 有应用会话 | 继续按会话开始次数计算，明确是已选目标应用 |
| 主动退出 | 有部分返回动作，旧聚合只包含返回 Focus／桌面 | 加入返回指定应用的动作映射，按统一口径统计 |
| 继续使用 | 旧统计只认 `continued`，新版操作记录为 `intentional_<n>m`、`rest_<n>m` | 新界面采用“回到任务／有目的使用／休息一下”，旧值做显式兼容映射 |
| 提醒率 | 当前模型没有明确字段 | 建议命名“提醒覆盖率”：所选期间开始的目标应用会话中，至少实际展示一次提醒的会话数 ÷ 该期间打开会话数；分母为 0 显示“—” |
| 专注时长 | 当前 `totalDurationMinutes` 是目标应用使用时长 | 首版显示“目标应用使用时长”；真正专注时长需另建开始／暂停／结束记录，不能拿任务计划长度或倒推值冒充 |
| 提醒活动 | 有按 attemptId 去重的实际展示表 | 按实际 displayedAt 聚合，需先处理额度重置删除历史的问题 |

“使用情况”建议改名为“提醒后的选择”，饼图按真实决策事件统计，点击展示数量和百分比。同一会话中的多次决策应分别记录，不能把会话数和动作数混为一个总数。

如果首版暂时不加决策事件表，只可展示“会话最后一次选择分布”，并明确这是有记录会话的末次选择，不是全部动作历史。无响应及旧数据缺项标为未记录，不能自动算成继续使用。

### 4.3 历史数据与查询

当前 `ReminderDisplayEventDao.deleteSince()` 被额度重置链路调用，会删除时间窗口内的真实展示记录。年度提醒活动上线前必须将额度状态与历史保留分开。

推荐：保留实际展示事件，额度重置写独立的重置标记／额度周期记录。额度计数和历史聚合使用不同查询，保持 attemptId 幂等。不能让“重置额度”改变昨天或今天的历史图，也不能让旧 attemptId 被误记成新展示。

新增或扩展：

- `ReminderActionEventEntity`：attemptId、sessionId、动作类型、选择时间、分钟数（如适用），每次已确认决策只记一次。
- 展示事件按日期统计查询、行为分布查询及稳定的日期区间模型。
- 统计业务放在 Repository／UseCase／纯聚合器中，Compose 只显示结果。
- 使用有上界的 `[start, end)` 查询，结束不超过当前实际时间；不要把尚未结束的会话累计到今天午夜之后。
- 处理跨午夜与跨范围开始的会话重叠。当前聚合只筛选范围内开始的会话，应针对“时长”补充重叠查询与裁剪，打开次数仍按开始时间算。
- 年度查询只取所需区间及聚合数据，避开把全年会话逐条反复送进界面；按当地时区处理日界线，补零、区分未来格及未知历史。
- 数据库迁移可以保留仍存在的旧数据，无法恢复以前已经删除的展示记录。历史动作也只有会话末值，不能伪造为完整事件历史。

### 4.4 今日状态占位

只在统计页保留此卡片，不把上一轮已移除的首页“今日状态”恢复。

- 标题：今日状态。
- 说明：状态总结即将上线。
- 暂不展示“比昨天更好”等无证据评价。
- 首版禁用跳转且不展示可点击箭头；组件可预留回调，正式功能接入后启用。
- 不自动调用 AI，不产生网络请求或额外统计任务。

## 6. 执行前需要确定的产品选择

1. 无有效任务时是否完全停止任务提醒？推荐停止；通用防沉迷若需要，应作为独立且可见的模式。
2. 时段外“设为当前”是否使用明确期限的临时专注？推荐是，防止再次出现无限延长。
3. 首版新任务是否统一跟随组时段？推荐是，旧任务保留原时段覆盖。
4. 年度活动是否优先月汇总柱状图？推荐柱状图；若优先还原参考图，则采用可横滑的日历热力图。
5. 首版是否接受“目标应用使用时长”这一真实指标？推荐接受，专注计时另立功能。

本方案先供审阅，不执行任务组迁移、提醒行为变更或统计数据结构变更。
