## 2026-09-03（提醒计数、预约到期与会话边界修复）

### 本次完成情况

- 「有目的使用」与「休息一下」的时间菜单不再使用固定 `220dp`，改为与对应按钮锚点等宽并从按钮左边缘展开。
- 强制提醒未选择就离开后，仍使用新的 `attemptId` 隔离 Activity 生命周期，但已经成功展示过的同一条逻辑提醒在重显时不再新增展示事件或重复消耗额度。若第一次启动在首帧确认前被打断，后续第一次真实绘制仍保留原展示类型并正常计数一次。
- 用户主动选择的定时跟进属于明确预约：到期且仍在原目标应用时，不再被普通窗口额度提前拦截；真正绘制成功后仍新增一次展示记录。已离开目标应用、守护关闭、会话关闭或锁屏等既有跳过/重试规则保持不变。
- 点击「回到任务」时，在打开 Focus 任务页之前立即停止并关闭当前目标应用会话。以后重新进入原应用会创建新会话，并按首次提醒延迟重新触发。
- 选择定时操作并完成调度后，主动清理本次普通任务召回通知，避免旧通知残留并被误认为倒计时到期通知。
- 关闭会话统一改为“先持久化结束状态并清空内存会话，再撤销提醒”。这避免撤销提醒发出的 Activity 关闭广播先取消当前协程，从而留下未关闭的会话。
- 点击「回到任务」后新增 30 秒承诺窗口：30 秒内回到同一目标 App，会为新技术会话立即显示一条强制提醒，但展示类型沿用不计数的强制重显，不新增额度或触达统计；再次点击「回到任务」会重新开始 30 秒。连续离开满 30 秒后再进入，才恢复普通新会话和首次提醒延迟。
- 承诺窗口文案使用即时本地“抓包”句作为第一行，并保留上一条按用户口吻生成的 AI 提醒正文。这样弱网/离线时也能立即弹出，同时继续体现温和、直接或犀利语气；犀利只针对反复返回行为，不攻击人格。

### 根因与验证

- 菜单宽度此前写死为 `220dp`；强制重显此前以新 attempt 直接调用展示事件写入；定时跟进在 Gate 与最终展示写入两层均受普通额度约束；「回到任务」此前只记录动作和导航，没有同步关闭 `AppSessionCoordinator` 持有的当前会话。关闭会话原先还会先发出取消提醒广播，存在 Activity 销毁取消 ViewModel 协程、使数据库会话未及时结束的竞争窗口。
- RMX3350 只读系统日志显示，系统曾明确允许 Focus 依靠悬浮窗权限从后台启动 `ReminderActivity`；问题时间附近没有新的 Activity 启动请求，因此本轮先修正应用内部额度与会话条件，不将其归因于免打扰或 ColorOS 拦截。
- 2026-09-03 再次只读检查确认：手机安装包最后更新时间为 2026-09-02 19:01:50，早于 2026-09-03 的定时提醒额度修复；系统 AlarmManager 同时记录到 Follow-up 闹钟唤醒。因此手机上“1 分钟有效、随后 5 分钟无弹窗”不能代表当前源码，符合旧 APK 在第一次跟进后被普通额度过滤的行为。
- 关闭会话顺序的专用回归测试已在修复后通过。随后一次完整本地测试发现 4 个旧测试仍固定断言“先取消、后关闭”；它们现已同步为新的安全顺序。用户随后要求停止编译与构建，因此这 4 项同步后的完整测试、AndroidTest 源码编译与 Debug APK 重建均留待用户后续手动执行。
- 本轮没有安装 APK，也没有自动操作手机。按用户要求，30 秒承诺窗口相关测试仅写入测试源码、未运行；菜单实际尺寸、同一提醒多次重显只计一次、1/5/10/自定义分钟到期全屏展示，以及回到任务后 30 秒内/外重新进入目标应用的行为均需用户重新编译安装后手动真机回归。

## 2026-09-02（第二轮真机反馈修复）

### 本次完成情况

- 根据 RMX3350 的只读通知状态复核，确认系统免打扰为关闭状态，而旧倒计时频道未启用横幅；倒计时通知升级到新的高重要性 `focus_follow_up_countdown_v3` 频道，使用默认通知声音并保持 `onlyAlertOnce`，只在倒计时开始时尝试显示一次顶部横幅。
- 「有目的使用」与「休息一下」的时长菜单保留各自锚点，并按按钮可用宽度计算水平居中偏移；菜单过宽时从锚点左侧开始，垂直方向仍交由 Material 处理。
- 设置修改状态提升到导航层；系统返回、顶部返回、底部标签切换，以及提醒请求打开任务页时，都经过同一保存确认。设置项仍沿用交互时立即持久化的现有机制，确认窗口承担离开前确认语义。
- 强制提醒新增“启动中 / 可见 / 待选择 / 稍后提醒转场”状态。用户未选择就用 Home 或最近任务离开后，回到同一目标应用会生成新的展示尝试并再次显示；每次完成首帧绘制都单独计数，强制重显即使超过普通窗口额度也继续，明确选择操作后才清除待选择状态。首帧记账确认完成前，操作按钮保持禁用。
- 补充 `singleInstance` 新 Intent 处理：新 attempt 到达时立即替换成不可操作的新提醒内容，并取消旧确认任务；注册表的状态修改同时匹配 session 和 attempt，异步结果只有在 Activity 仍处于前台且 attempt 一致时才能原子提交，避免旧 attempt 覆盖或关闭新提醒。

### 验证结果与边界

- 完整 JVM 单元测试共 265 项，失败 0、错误 0、跳过 0；AndroidTest 源码编译通过；`git diff --check` 无空白错误。
- 按用户要求，本轮没有运行 connected AndroidTest、没有构建或安装 APK、没有自动操作手机。顶部横幅、菜单视觉位置、四条离开路径和 Home/上滑后的强制重显仍需用户在 Android Studio 中手动回归。
- Android 通知频道创建后，其重要性和横幅开关可继续被系统或用户修改；如果 `v3` 频道仍不显示顶部横幅，需要在系统的 Focus 通知设置中确认该频道允许横幅和声音。

### 本次完成情况

- 首页已增加实时模式的无障碍运行状态诊断；设置页已完成问卷星反馈入口及微信、支付宝支持二维码展示。
- 本次将开发日志、任务清单和交接说明一并整理后提交到 GitHub 的 `feature/focus-v0.1-preview` 分支，便于后续从同一版本继续验证和开发。

### 已确认但尚未关闭的风险

- 通过 USB 在 realme RMX3350（Android 11 / ColorOS V11.1）观察到：Focus 的前台服务、跟进闹钟和作业仍存在时，无障碍服务可能处于系统显示已开启但未绑定的状态，应用进程也可能被 ColorOS 放入 `freezer:/frozen`。这会使实时模式失去前台应用事件，不能视为“后台可靠”已经完成。
- 当前前台服务只能提高进程存活机会，不能保证 OEM 不冻结无障碍服务；不会用高频轮询或绕过系统限制的方式换取表面保活。

### 下一步优先级

1. 为实时模式增加可解释的临时兼容检测兜底：无障碍失联时短暂使用兼容检测，并在首页明确显示降级状态；用户原先选择仍保持“实时模式”。
2. 在可靠性回归后，再加入用户主动发起的结构化诊断导出：仅收集本应用事件、先预览再通过系统分享发送，不读取完整 Logcat、不静默上传任务内容或无障碍文本。
3. 如选择 Google Play 发布渠道，按其 2026 年 8 月底的要求迁移并验证 target API 36；其他渠道也应完成 Android 11～17 的机型回归。

### 验证边界

- 按用户要求，本次未运行 Gradle、未编译或安装 APK；提交证明的是源码、文档和 Git 交付完整，当前头部版本仍需由 Android Studio 构建后进行真机回归。

## 2026-08-14（ColorOS 冻结下的再次提醒修复，待真机计时复测）

### 真机证据

- 设备为 realme RMX3350、Android 11。Focus 的前台服务和无障碍服务仍显示运行，
  但应用进程已经进入内核 `freezer:/frozen`。
- 10:28 选择「1 分钟后提醒」，Room 已记录 10:29 的 `snoozeUntil`；到 10:35，
  对应 WorkManager 任务仍为 `ENQUEUED`，进程内协程与 JobScheduler 均未执行。
- 因此当前失败不是 AI 文案、提醒额度或弹窗门控问题，而是到期逻辑没有获得运行机会。
- 手机当前是旧基础 APK 加 Android Studio Apply Changes 覆盖层的混合运行状态；最终验证必须使用完整构建和安装，
  不能继续以热替换结果作为发布证据。

### 已确认设计

- 保留现有 Room 截止时间、进程内协程和 WorkManager，在其外增加一次性 `AlarmManager` 唤醒路径。
- 系统闹钟只作为不可见的调度器；到期后仍由 Focus 的统一执行器检查守护状态、当前目标 App、
  原会话和提醒额度，并显示 Focus/DeepSeek 个性化提醒，不使用系统闹钟界面或系统闹铃。
- Android 11 使用 `setExactAndAllowWhileIdle`；Android 12 及以上已有精确闹钟能力时继续精确调度，
  否则自动降级到 `setAndAllowWhileIdle`。本轮不强制增加权限提示。
- 离开目标 App、关闭守护或替换稍后时间时，必须同步取消系统唤醒、WorkManager 和进程内任务。
- 三条路径同时到期时复用 `claimSnooze()` 原子领取，只允许一次弹窗和一次额度计数。

### 已实施

- 新增 `FollowUpAlarmScheduler`、`AndroidFollowUpAlarmScheduler`、
  `FollowUpAlarmReceiver` 和可单测的 `FollowUpAlarmHandler`。
- `HybridFollowUpScheduler` 现在同时登记进程内协程、WorkManager 与一次性 AlarmManager 唤醒；
  任一路成功、离开目标 App、关闭守护或重新选择稍后时间时统一取消其余路径。
- Alarm 到期后仍调用 Focus 原有 `FollowUpReminderExecutor`，继续复用目标 App、守护状态、
  锁屏条件、提醒额度、AI 文案和 `claimSnooze()` 去重；不使用 `setAlarmClock()`，
  不显示系统闹钟界面或播放系统闹铃。
- 锁屏等临时条件不满足时，以 15 秒为间隔重新布防，最多 20 次，避免无限唤醒。
- 首页「守护控制」新增实际滚动窗口额度：
  `本时段（N 分钟）已提醒 X/Y 次`；点击重置额度后立即刷新为真实数据库计数。

## 2026-08-06

### 问题 1：提醒弹窗不出现（真机实测）

**现象**：安装后页面显示正常，但打开目标 App 后没有任何提醒弹窗；首次打开 App 时也没有权限提示。

**根因分析**（按调用链逐层排查）：

1. 引导页选择检测方式后，只跳转系统设置页并标记引导完成，**没有把所选模式写入应用设置**。
   `enableAccessibility` 默认值为 `false`，且唯一的写入点是设置页的「启用无障碍检测」开关。
2. `FocusAccessibilityService.shouldProcessAccessibilityEvents()` 要求
   `detectionMode == REALTIME && enableAccessibility` 同时成立；开关为 false 时，
   无障碍事件在入口被直接丢弃 → 不产生会话 → 不触发提醒。
3. 兼容模式同理：`MainActivity` 仅在 `detectionMode == COMPATIBILITY` 时启动检测服务，
   引导页同样没有写入该值，服务不会启动。
4. 「首次打开无权限提示」符合当前设计（应用不主动请求权限，仅由引导按钮跳系统页）；
   一旦完成过引导（SharedPreferences 标记），之后直接进入首页。

**修复**：

- 引导页选择检测方式时即调用 `SettingsViewModel.applyOnboardingDetectionMode(mode)`，
  持久化 `detectionMode` 与 `enableAccessibility`。
- 设置页监听生命周期：实时模式下若系统无障碍已开启，自动把应用内开关置为开启
  （`ensureAccessibilityEnabled()`），即使之前没手动开开关也能恢复检测。
- 「启用无障碍检测」开关与实时模式选中时，未开启则跳转系统无障碍设置页。
- 引导页进入 AI 配置步骤时（Android 13+）请求通知权限，实时模式同样覆盖。

### 问题 2：弹窗可能被静默吞掉（悬浮窗与通知权限）

**现象**：即使检测链路通了，也可能看不到任何提醒。

**根因分析**：

1. 提醒展示依赖「显示在其他应用上层」（SYSTEM_ALERT_WINDOW），
   无权限时降级为通知；但应用内**没有任何地方引导用户开启悬浮窗权限**。
2. Android 13+ 通知需要运行时权限，实时模式路径此前不会请求通知权限；
   通知被拒绝时降级通知也会被系统丢弃。

**修复**：

- `PermissionHelper` 增加悬浮窗权限检测与跳转（`ACTION_MANAGE_OVERLAY_PERMISSION`）。
- 设置页「检测方式」分组新增悬浮窗权限状态行与「去开启」入口，并在返回页面时刷新状态。
- 切换到任一检测方式时都会请求通知权限（Android 13+）。

**验证方式**：Android Studio 构建后真机复测——目标 App 打开后停留超过提醒延迟，
应出现悬浮窗弹窗或通知；首次引导完成后检查设置中的检测方式与无障碍开关状态。
